# VEILBENCH Phase 6 — Docker build and real MPC end-to-end verification

## Goal

Phase 6 moves from static production preparation to verifiable container builds
and a repeatable public three-founder test. It does not claim that a VPS or
Vercel project has already been deployed.

The production frontend remains on Vercel. The VPS runs PostgreSQL, the
coordinator, three independently configured MPyC party containers, and Caddy.

## 1. Sequential production image build

A low-cost academic VPS can run out of memory if several Python images build at
the same time. The deployment process now pulls PostgreSQL and Caddy first,
then builds the backend and each party service one at a time.

From the VPS project root:

```bash
sudo bash scripts/build_production_images.sh .env.production
```

This validates the Compose configuration, checks the Docker daemon, pulls the
external PostgreSQL/Caddy images, and builds the backend plus all three party
images sequentially. It does not start, stop, or replace running containers.

The normal deployment script invokes the same build helper and then starts the
services with `up -d --no-build`. If an image build fails, the existing running
stack is left untouched.

## 2. Deploy after the build succeeds

```bash
sudo bash scripts/deploy_vps.sh
```

The deployment script validates the production environment and certificates,
validates the Caddyfile, runs the sequential image build, starts the services,
checks internal mTLS, and runs read-only public HTTPS smoke tests.

It never runs `docker compose down -v` and does not delete persistent volumes.

## 3. Run a real synthetic three-founder MPC test

After the public smoke tests pass, run this explicit test from the VPS host:

```bash
python3 -m backend.ops.smoke_test_mpc_e2e \
  --env-file .env.production \
  --confirm-synthetic-data
```

This command intentionally creates one short-lived session and submits only
synthetic academic demonstration values (50,000; 70,000; 60,000). It then:

1. Creates a session through the public coordinator API.
2. Checks the invitation payload is marked `Cache-Control: no-store`.
3. Verifies each invitation points to its matching public party endpoint.
4. Sends each synthetic salary directly to its assigned party using its
   single-use capability. The coordinator request contains no salary.
5. Polls until all three parties are reported as submitted and the session is
   READY.
6. Starts the MPC computation through the coordinator.
7. Verifies the completed result contains exactly `aggregate_sum` and
   `average_salary`, with expected values 180,000 and 60,000.0.

The script never prints individual values, founder capabilities, or the admin
token. The explicit `--confirm-synthetic-data` flag is required because this
command performs a real computation and creates a session.

This public HTTP smoke test exercises the same API/party routing used by the
browser, but it is not a substitute for the final manual demonstration using
three separate browser sessions.

## 4. Windows development checks

The Docker production build and public end-to-end test must run on a Docker
host and, for the public smoke test, after the VPS is reachable. On Windows,
continue to run:

```powershell
.\.venv\Scripts\python.exe -m compileall -q backend scripts
.\.venv\Scripts\python.exe -m pytest backend\tests -q
```

For the frontend:

```powershell
cd frontend
npm ci
npm audit
npm audit --omit=dev
npm run lint
npm run typecheck
npm run build
```

The local frontend lockfile generated by `npm install`/`npm ci` must be kept in
the project and committed to Git. The production VPS does not build the
frontend image; Vercel builds the Next.js frontend separately.

## 5. Completion criteria

Do not call Phase 6 complete until the target environment demonstrates:

- `docker compose config --quiet` succeeds on the VPS.
- PostgreSQL, backend, three parties, and Caddy images build successfully.
- Alembic migrations complete and the backend becomes healthy.
- Internal mTLS accepts trusted clients and rejects anonymous TLS clients.
- Public CORS and founder-input smoke tests pass through Caddy.
- The synthetic three-founder test completes with aggregate 180,000 and
  average 60,000.0.
- PostgreSQL and each party's replay guard survive a controlled restart.
- The final browser demonstration works using three separate founder sessions.

Three Docker containers on one VPS are separate processes and credentials, not
independent administrative trust domains. The VPS administrator can control
all three parties; disclose this limitation in the academic presentation.
